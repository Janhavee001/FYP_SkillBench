Setup02 / 17

Why run the code instead of reading the claims

I wanted to know what the existing work does, not what the abstracts say it does. In two of the five cases the shipped code does not implement what the paper implies.

The five papers also cannot be compared as published. Two are benchmarks with their own data and metrics. Of the three systems, LIDA self-evaluates with an LLM, Data Formulator 2 has no quantitative evaluation at all — only a ten-person user study — and nvAgent uses VisEval with an MLLM judging rendered images.

Placing their published numbers side by side would mean nothing. So I built a shared test set and a shared rubric, and ran the two native benchmarks separately on their own terms.

Three research questions

  • RQ1 — do structured skills improve correctness over a plain LLM baseline?
  • RQ2 — can an agent reliably select and compose skills for unseen data?
  • RQ3 — does validation or self-correction improve reliability?

None of the three can be answered from the five papers alone, because the systems differ in model, scaffolding and output format all at once. That is what the two controls are for.

Method05 / 17

The shared test set, and two controls

Sixteen questions, two public datasets

DatasetRowsColsWhy this one
Titanic89115mixed categorical and numeric, with real missingness — deck 77% missing, age 20%
Wine Quality (red)1,59912eleven continuous predictors against an ordinal target, 82% of wines at quality 5 or 6

Eight questions each, tagged stat, viz or mixed: descriptive statistics, hypothesis testing, correlation, distributions, outliers, regression and classification, missing data, and pure visualisation.

Ground truth is computed, not typed

datasets/build_questions.py derives every reference_answer from the actual CSV with scipy and scikit-learn. Spot-checked against values I already knew: Titanic survival 0.3838 overall, 0.742 female, 0.1889 male; wine alcohol–quality r = 0.476. Re-running regenerates everything.

Two controls, one variable each

RQ1 control

baseline_plain — one prompt, one shot, no execution feedback, no retry.

RQ3 control

baseline_selfcheck — same prompt, same model; when the generated code raises, the traceback is fed back for exactly one repair attempt.

Comparing plain against selfcheck isolates self-correction inside a fixed architecture — same model, same prompt, same questions, one variable changed. Without that pair, nothing in the five papers separates architecture from scaffolding from model.

Each question also carries expected_method, acceptable_methods, expected_chart and a numeric tolerance — which is what lets method selection and output correctness be scored programmatically rather than by eye.

Method07 / 17

Two safeguards against my own benchmark

Safeguard 1

Coverage flags, never a zero

When a system structurally cannot exhibit a dimension, that dimension scores null with coverage=False — never 0.0 — and the comparison prints how many items each score actually rests on.

This turned out to matter far more than expected. Two of the seven conditions are unscorable on half the rubric.

Safeguard 2

The judge declares itself

Without an API key the interpretation dimension falls back to a transparent keyword heuristic and stamps judge="heuristic" on the output.

A keyless run can never be mistaken for a judged one. Every figure in this deck carries judge="llm".

And a test suite

23 checks that the rubric discriminates

harness/test_rubric.py asserts that chi-square outscores a t-test on a chi-square question, that a pie chart loses to a bar chart, that executability is strictly ordered, and that wrong numbers score below right ones.

Runs without an API key.

I built both of these after deciding that a benchmark which overstates its own precision is worse than no benchmark at all.

Output channels differ too, which is the underlying reason. LIDA emitted stdout on 0 of 16 questions — its answer is a rendered image. Data Formulator 2 returns numeric outputs and a 140-character note. nvAgent returns 109 characters of schema reasoning and no chart artifact my harness can read.

Why LIDA's correctness is blank

Recovering its numbers would mean reading them off a chart — which is what VisEval's MLLM judge does and mine does not. Scoring it 0.0 would measure my harness, not LIDA.

Why StatABench's is blank in two columns

Its agent answers by calling MCP tools, so its records carry no generated code. Scoring that 0.0 for "no code emitted" measures interaction style, not capability. Its answers are closed-form by design — "The answer is (63.43 kg, 72.57 kg)" — so judging them as interpretation measures the question format.

Before coverage was applied properly, StatABench appeared with an overall of 0.042 against a native accuracy of 75%. Its benchmark's own adjudication is now carried through as the correctness score instead.

Results10 / 17

Statistical questions versus visualisation questions

The table that does most of the explanatory work — it separates a genuine capability gap from a category mismatch.

statistical questions visualisation questions

Quoting only the overall figure would misrepresent all three systems.

nvAgent is the clearest case. Its VQL grammar is Visualize <TYPE> SELECT … — a chart-over-SQL language with no way to express fitting a logistic regression. It emitted no VQL at all for three of the sixteen questions.

That is an expressiveness ceiling, not a defect. On its own VisEval benchmark it outperforms its baselines.

The transferable finding: scaffolding designed for visualisation does not transfer to analysis. All three systems lose heavily on stat items specifically.

Reading the results12 / 17

What the numbers mean

On the baseline

The plain baseline wins — but only narrowly, and only here

selfcheck at 0.804 beats every published system. The result is real and much narrower than it looks: on standard questions over well-known datasets, an unscaffolded model already picks the right method 98% of the time — chi-square for the association question, Welch's t-test for the group comparison, logistic regression for the binary outcome, essentially every time.

This is not evidence that scaffolding is useless. It is evidence that my test set is not hard enough to require it.

On interpretation

None of the three systems interprets its own results

All three produce narrative — LIDA averages over 1,700 characters of it — but the judge, applying StatABench's anchors, found almost none of it interprets the result.

  • LIDA describes the chart's design: the colour palette, the dashed reference line, the axis labels.
  • Data Formulator 2 returns a single-line encoding recommendation.
  • nvAgent returns reasoning about the schema.

Every one of these tools hands back an artefact and leaves interpretation entirely to the human.

On category

The visualisation systems really are much stronger at visualisation

LIDA scores 0.473 on statistical questions and 0.750 on visualisation ones. The overall column flattens that distinction away.

This is also the main threat to the headline table's validity, and I have to own it: my questions ask for the test statistic and the p-value, which rewards systems whose output channel is text and penalises systems whose output channel is an image.

Reading the results13 / 17

Where reliability actually fails

A validator only repairs what it may touch

nvAgent's Validator reported fixed=True fourteen times and fixed nothing

In its first run it burned all three rounds on fourteen of sixteen questions, reporting success each time, and never resolved the error — because the fault lay in its own scaffolding template rather than in the LLM-generated code the refiner is scoped to rewrite.

An execution-feedback validator detects that something failed but can only fix the region it is allowed to edit. A validator that checked schema conformance or method appropriateness would catch a different — and more important — class of error.

Grounding fails silently — the RQ2 problem

nvAgent, on the wine correlation question

SELECT property, corr FROM (
  SELECT 'fixed_acidity' AS property,
    CORR(fixed_acidity, quality) AS corr
  FROM wine UNION ALL ...
) AS t ORDER BY corr DESC

The chart choice is right. The statistical intent is right. It queries a table called wine, which does not exist — the Processor had given it wine_quality. The system invented a plausible-looking table name and failed on that alone.

Selection is largely solved. Composition and grounding are not. The agent chose correctly and still produced nothing, because it did not bind to the data it had been given.

Limits14 / 17

Ten bugs I found in my own harness

Recorded in full because they turned out to be one of the more useful findings of the exercise. Every one would have produced a confident, wrong result.

#What brokeWould have been reported as
1Windows console cp1252 vs. the model's U+2011 / U+2192every system penalised on code executability

6cp1252 again, in a separately spawned subprocessStatABench scoring 0% — 25 responses of 'charmap' codec can't encode '⏳'

8httpx ≥ 0.28 against a pinned openai 1.39DataSciBench generating nothing
9wrong ground-truth tree copiedDataSciBench scoring 0.0 on everything — cleanly and plausibly
10mixed scales in the results CSVa "completion rate" of 1.36

All ten made a system look worse than it is. None flattered one.

Most were invisible in the aggregate scores and only surfaced when I read individual records — because a plausible-looking number (0/16, 7/16, 0%, 1.36) is indistinguishable from a real result until you inspect the output underneath it.

Bug 6 also shows that fixing a class of error once is not enough: the same cp1252 root cause reappeared at two further process boundaries hours later. Fixes 2 and 3, and the coverage rule, are now locked in by regression tests.

For a project about reliable analysis this is direct evidence. An agent that reports a confident aggregate without exposing per-item provenance will mislead its user — and the failure mode looks systematically pessimistic while actually being arbitrary.

Limits15 / 17

Which of my own numbers I do not trust

nvAgent was measured three times

RunResultCause
first0/16bug 4 — mine
second7/16bug 5 — mine
third12/16honest

Only the third is reported. Had I published the first, my report would have claimed that the one paper whose entire contribution is a validator agent cannot execute anything — when in fact it was producing correct VQL every time.

And it is not deterministic. Even at temperature 0, titanic_q8 produced valid VQL in one run and nothing in another. Its single-run figures carry more uncertainty than the others'.

  • Both native runs are subsets. StatABench ran on 20 tool-requiring items, DataSciBench on a single task across three runs. These demonstrate the pipelines work end to end; they are not publishable benchmark numbers. StatABench's own pipeline also skips every item flagged code == 0, so even a full run attempts 198 of 404.
  • My test set favours systems that print numbers. Asking for the test statistic and the p-value penalises systems whose output channel is an image. This is the main threat to the headline table.
  • The model differs from the papers'. An open-weights model through OpenRouter, not the models they used — StatABench reports GPT-5.1 at 68.6% on Stat-Closed. This study compares architectures on a fixed model; it does not reproduce published scores.
  • Three of the five repositories do not run as shipped. nvAgent cannot even be imported as distributed. Six isolated virtual environments were needed, because the repositories pin mutually incompatible dependencies.
Conclusions16 / 17

Answers, at the confidence the evidence supports

RQ1 — not demonstrated

Do structured skills improve correctness over a plain LLM baseline?

And the test set is the reason. The plain baseline reaches 0.981 on method selection, which leaves essentially no headroom. Structured skills cannot be shown to help where an unscaffolded model already chooses correctly 98% of the time.

The useful finding is negative: none of the three published systems beats the plain baseline overall, and all three lose heavily on statistical questions. Scaffolding built for visualisation does not transfer to analysis.

To answer this properly I need harder tasks — unusual data shapes, methods that must be named rather than inferred, multi-step compositions a single prompt cannot hold.

RQ2 — half answered

Can an agent reliably select and compose skills for unseen data?

Selection is largely solved on familiar data; composition and grounding are not. The failures were not wrong tests:

  • right chart, table that does not exist (nvAgent)
  • no plan at all, question outside the grammar (nvAgent, ×3)
  • prose returned instead of code (Data Formulator 2, ×2)

StatABench's 36-tool registry is the only skill-registry-shaped artefact among the five, and it belongs to a benchmark. No published system here composes from a skill library.

RQ3 — yes, best supported

Does validation or self-correction improve reliability?

A single repair pass on an otherwise identical baseline raised clean execution 0.625 → 0.812 and correctness 0.637 → 0.771. nvAgent's validator fixed 8 of 22; LIDA's repair fixed 3 of 7.

Two qualifications. Execution rate confounds with task complexity — Data Formulator leads that column with no validator at all. And a validator only repairs what it is scoped to edit, so execution-feedback validation catches crashes but not analyses that are wrong yet runnable.

Conclusions17 / 17

What I intend to build

Five design commitments, each traceable to a result above rather than to a preference.

  1. Include a validator — and give it more to check than execution

    The best-evidenced result I have. But execution-only validation misses the errors that matter most, so mine should also check schema conformance and method appropriateness.

  2. Treat interpretation as a first-class output

    All three published systems score near zero here. Producing a chart or a number without saying what it means is the clearest unmet need in this literature.

  3. Use an explicit skill registry — but justify it on composition, not selection

    Selection is close to saturated for a strong model on familiar data. The defensible argument for a registry is reliable composition and grounding.

  1. Avoid a rigid intermediate grammar

    nvAgent's VQL is the cautionary case. It guarantees a valid chart but cannot express a hypothesis test or a model fit — and it fails silently, by emitting nothing.

  2. Design the evaluation before the agent

    Ten measurement bugs in this study all favoured a wrong conclusion, and most were invisible without per-record inspection.

Reproducibility

Harness, rubric, computed ground truth, per-system JSON and the seven-row comparison all live in benchmark-fyp/. Every adaptation to a shipped repository is recorded in README.md, and the two-line nvAgent import fix is visible in git -C repos/nvAgent diff.
